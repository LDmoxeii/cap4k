# Outcome

Audit Generator, Runtime, and Analyzer after the Skill responsibility reset from PR #153, preserve the decisions in one continuous audit context, and determine when the combined four-block system is coherent enough to begin downstream real-project validation.

# Scope

- Treat the merged thin Skill and machine-readable Agent API direction as the accepted Skill baseline.
- Audit Generator first, then Runtime, then Analyzer against current mainline contracts, implementation, tests, public documentation, Agent API facts, and relevant open issues.
- Audit the semantic round trip `Design JSON -> generated skeleton -> Analyzer -> Drawing Board`, including whether every accepted design field is materially represented and recoverable without manual structural repair.
- Classify findings as verified, partial, drift, missing-core, provider/extension, or downstream-evidence.
- Discuss findings before any implementation is authorized.
- Re-evaluate an affected block after an independently implemented fix has merged to `master` and has been brought back to the audit line.
- Produce a combined downstream-readiness decision only after all three remaining blocks have been audited.

# Non-goals

- Do not validate the reference project before the three remaining block audits are complete.
- Do not claim that cap4k covers every strategic DDD concept or can prove domain correctness.
- Do not repair Generator, Runtime, Analyzer, documentation, or downstream projects opportunistically on the audit branch.
- Do not create separate Generator, Runtime, or Analyzer audit branches.
- Do not preserve compatibility for hypothetical users through aliases, shims, dual paths, migration bridges, deprecation periods, or legacy fallback behavior.
- Do not reopen the retired Bootstrap capability.

# Acceptance examples

- Given a Generator contract advertised by descriptors, documentation, or Agent API facts, the audit identifies the actual source, canonical model, planner/template, output ownership, conflict policy, and proportionate tests, or records a specific discrepancy.
- Given a Runtime boundary such as reliable event payload persistence, the audit treats the current runtime semantic boundary as authoritative and identifies generator or documentation drift without weakening that runtime boundary.
- Given an Analyzer observation, the audit distinguishes structural evidence from business truth and identifies freshness, coverage, and transport limitations.
- Given a supported Design JSON entry, generation produces a structurally complete skeleton, Analyzer recovers the same tactical design, and the resulting Drawing Board can regenerate an equivalent skeleton without silently losing or inventing design semantics.
- Given a generated handler, subscriber, domain service, or other behavior surface, business policy may remain handwritten, but compilation shape, declared types, annotations, artifact selection, wiring contracts, and other framework-owned structure do not require manual completion caused by a generator omission.
- Given a finding that requires implementation, the audit records the decision and expected acceptance evidence while leaving the code unchanged on this branch.
- Given a fix merged independently to `master`, the audit refreshes from that mainline fact and re-runs the affected gate before changing its conclusion.
- Downstream validation is not opened while any unresolved missing-core or cross-block drift finding remains.

# Constraints and invariants

- `docs/framework-capability-audit` is the only continuous audit and decision branch.
- Framework fixes use isolated short-lived `feature/*` or `fix/*` branches and enter `master` through the repository's normal pull-request path.
- Cap4k currently has no external users; breaking iteration is allowed and a single clean current contract is preferred.
- Humans own strategic/domain decisions and acceptance. Agents assist investigation, translation, implementation, and verification without claiming business authority.
- Skill routes; Generator projects explicit inputs and canonical models; Runtime owns real execution semantics; Analyzer supplies structural observation and engineering evidence.
- Analyzer output never feeds Generator automatically. Any use of a Drawing Board as authoring input remains an explicit human/Agent action.
- `Design JSON`, its generated skeleton, and the Analyzer Drawing Board must represent the same normalized tactical design. File names, file counts, and physical partitioning may differ; semantic content may not.
- Framework-owned skeleton structure must be complete. Handwritten business behavior is outside this equality contract and remains a human/Agent implementation responsibility.
- Current repository facts outrank historical chat, stale issue text, and old plans.
- PR #152's runtime refusal to persist reliable-event entity payloads is an accepted boundary and must not be reversed as a generator fix.

# Decisions

- PR #153 completed the Skill responsibility reset and is the baseline for this audit.
- Audit the remaining blocks sequentially in this order: Generator, Runtime, Analyzer.
- Keep audit artifacts and cross-block decisions on one branch to minimize context loss.
- Findings are discussed before implementation; implementation is forked into another session and branch by the user when accepted.
- Perform one combined downstream validation only after all four blocks have a coherent current contract.
- Compatibility work requires future evidence of a real consumer and an explicit compatibility requirement.
- Scheduled Reaction remains a handwritten application Job/reaction surface. Remove it from the Design JSON capability descriptor and generated-skeleton claims; do not add a first-class tag, canonical carrier, planner, template, or runtime execution contract in this audit cycle.
- Strong ID Spring MVC path/query binding is part of the Generator gate. Every generated Strong ID must expose a JVM-static String factory that delegates to the existing semantic parser; Runtime must not add reflection-based conversion machinery. Verify the contract with real MVC path and query binding tests.
- Retire the standalone Python generator-input validator and its public documentation surface. Authoritative validation belongs to the actual source providers, canonical assembler, `cap4kPlan` diagnostics, and Agent API evidence; do not preserve a second partial parser or compatibility command.
- Read-model weak-reference projection remains an optional provider/extension boundary. The built-in `aggregate-projection` stays opt-in, adapter-owned, scalar-only, and without read-model runtime; `@RefAggregate` remains a typed scalar identity reference and does not create an automatic projection object relation.
- Do not create automatic Analyzer-to-Generator feedback. Instead, require a semantic round-trip contract: `Design JSON == generated skeleton == Drawing Board`, modulo physical file representation and explicitly accepted non-semantic normalization.
- A generator defect may not force humans to repair framework-owned skeleton structure. All accepted design declarations must be generated into a compile-valid, runtime-contract-complete structural surface and remain recoverable by Analyzer; only domain behavior and business decisions remain handwritten.
- Compare round trips by normalized tactical semantics, not literal JSON text. Normalization may ignore file names/count/partitioning, JSON formatting, file/entry order, artifact order, omitted optional empty arrays, omitted defaults versus the same effective defaults, and type-expression spelling that resolves to the same canonical FQN. It must preserve field/result-field and nested DTO order, resolved type identity, nullability, default semantics, artifact set/variant, event direction, persist/eventName, and runtime annotation semantics.
- Keep `domain_service` as a metadata-only design anchor. It may declare identity, package, description, aggregate ownership, and its `domain-service` artifact, but must reject non-empty `fields` and `resultFields`. Generator emits the annotated service class anchor; business methods remain handwritten, and Analyzer does not infer operation contracts from method bodies. A future first-class operation schema requires a separate confirmed design.
- Require every accepted Design JSON entry to select a non-empty, tag-compatible artifact set containing its primary structural carrier. Secondary query/capability handlers and domain/integration subscribers are valid only alongside their primary contract/event; `integration-subscriber` additionally requires `integration-event:inbound`. Reject explicit empty artifacts, cross-tag families, and secondary-only selections. Omitted `artifacts` continues to expand to the documented defaults; do not add a metadata-only generated carrier.
- Preserve the shared `defaultValue` contract for Domain Event and Integration Event fields. Generator must render the supported stable default-expression subset on event payload and nested DTO constructors, and Analyzer must recover the same normalized default semantics. Whether using a default is domain-correct remains an authoring decision; event templates may not silently discard an accepted default.
- Require non-blank `domain_event.eventName` when `persist: true`; keep it optional for transient Domain Events. Generator must project a present name into `@DomainEvent(value = ..., persist = ...)`, and Analyzer must compare the authoring metadata name with the runtime annotation value and fail on conflict. A persisted event may not have an empty runtime `eventType`.
- Keep explicit BINARY-retained annotation metadata as the lossless carrier for Drawing Board and flow recovery, but move and rename `BuildingBlock` and `AggregateElement` out of `ddd-core` into a dedicated compile-time analysis-metadata contract/module with no runtime meaning and a compile-only project dependency. Default generator templates emit this metadata. Projects may remove it in custom templates when they intentionally opt out of Drawing Board and the corresponding analysis recovery. Do not introduce a sidecar skeleton index in this cycle.
- Fail fast when a requested Drawing Board or flow-analysis task lacks metadata required for complete recovery. Diagnostics must identify the missing symbols, affected capability, and how to restore the default metadata-emitting templates or annotations. Never silently omit unannotated elements or emit a complete-looking partial Drawing Board.
- Permit `entity` as an ordinary Domain Event payload field name. Remove name-based filtering from canonical assembly and Analyzer recovery, and rely exclusively on the resolved recursive semantic type validator to reject actual Entity/Aggregate payload types. Preserve PR #152's runtime refusal to persist reliable-event entity payloads.
- Treat `pageNum/pageSize` on `page` Query and API Payload variants as framework-owned PageRequest structure implied by the variant, not ordinary Design JSON fields. Generator keeps deriving them; Analyzer excludes them only after confirming the page carrier and PageRequest semantics, never by global name filtering. Reject explicit same-name fields on a page variant, allow them on non-page variants, and keep `1/10` as the current variant default contract until a separate explicit page configuration is designed.
- Emit stable type identities in Drawing Board: use normalized short names only for Design JSON builtins, standard containers, and nested DTOs declared by the current building block; emit resolved canonical FQNs for Strong IDs, Value Objects, enums, other project/context types, and external types. Apply the rule recursively inside containers, and never choose a short name merely because the current analysis classpath happens to make it unambiguous.
- Retain `Array<T>` as a first-class Design JSON type and implement lossless Analyzer/Drawing Board recovery for recursive container nesting, element/container nullability, and normalized `emptyArray()` defaults. Keep recursive reliable-event payload validation. Primitive arrays such as `IntArray` and `ByteArray` remain outside the current contract.
- Preserve declaration order for `fields`, `resultFields`, and every nested DTO. Drawing Board may normalize artifact, file, and entry order, but constructor position is tactical semantics and must not be sorted away.
- Deliver Generator repairs through four focused branches/PRs: `fix/generator-contract-surface`, `fix/strong-id-mvc-binding`, `feature/analysis-metadata-contract`, then `fix/design-roundtrip-contract`. The first three may run in parallel from current `origin/master`; the round-trip branch starts only after the metadata-contract PR has merged and includes the real seven-tag gate plus required TestKit isolation. Refresh this audit line from merged `master` evidence after each PR. Keep G-06 optional and G-07 outside the blocking repair set.

- Replace the current hand-written Issue #92 pseudo-round-trip with one real gate using two clean project copies. Project A must generate and compile all modules, run the real compiler Analyzer on the generated sources, and emit Drawing Board files. Project B must disable the original Design JSON, use only Project A's Drawing Board files as explicit ordinary Design JSON inputs, regenerate, and compile. Compare normalized canonical projections and the two generations' framework-owned skeletons; a hand-written `design-elements.json`, a second `plan` without generation, or a single shared generated tree is not evidence.
- Evaluate analysis completeness per configured analysis input directory. A complete module must not mask a second module that contains candidate nodes but lacks the metadata/evidence required for complete Drawing Board recovery; the combined request must fail rather than emit a partial board.
- Satisfy Issue #102 through directly Design-JSON-compatible Drawing Board output and explicit human/Agent import. Cross-context outbound-to-inbound variant conversion remains an explicit context decision; the framework must neither auto-register Drawing Board output nor auto-flip event direction.
- Isolate the real gate from H2 file locks with a temp-project-unique in-memory fixture URL and no `DB_CLOSE_DELAY=-1`. Do not change production JDBC lifecycle or mechanically rewrite unrelated fixtures in this branch.
- Select exactly one outbound Integration Event transport provider per application/Bounded Context. Multiple publisher providers are a deterministic startup conflict; Core does not broadcast one `EventRecord` across HTTP, RabbitMQ, and RocketMQ providers.
- Remove generated public Spring Data repository interfaces. `Mediator.repositories` remains the business repository entry; generated JPA structure becomes a private cap4k adapter/carrier backed by `EntityManager` or another provider-private implementation, and Generator/Analyzer must preserve that carrier in the design round trip.
- Replace FastJSON and Gson with Jackson across Runtime and build tooling under one stable semantic codec contract. Do not retain fallback codecs or compatibility paths; verify Strong ID scalar encoding, reliable persistence, transports, Agent API, Design JSON, and Drawing Board determinism.
- Treat deterministic local provider/configuration errors as startup failures. Temporary external broker unavailability keeps the application alive with observable `DEGRADED`/`RECOVERING` state, durable outbound retry, subscriber reconnection, and truthful health/readiness rather than silent omission.
- Preserve separate reliable Command and Event records while sharing a provider-internal claim/lease/retry/retention substrate and focused tests. Retire the public `Locker` API, JDBC Locker modules/starter/table/configuration, and runtime-owned MySQL partition DDL; each JPA provider owns DB-native atomic due-record claiming with DB time, short transactions, and claim tokens/version checks.
- Keep reliable Integration Event delivery intentionally simple: one event/outbox record, one state for the selected transport, and no per-consumer or per-handler delivery table. Transport confirmation marks `DELIVERED`; explicit failure, missing confirmation, timeout, or ambiguous outcome remains retryable, so stable event IDs and idempotent consumers are required by the at-least-once contract.
- Reposition HTTP as a non-production experience transport with one configuration shape only: static `routes[eventName] -> baseUrl`. The same mapping supports remote delivery and explicit self-consumption by routing to the current application. Remove dynamic subscribe/unsubscribe and inspection endpoints, subscriber registries and their JPA persistence/starter/table, `eventName@registerUrl`, service discovery, and broadcast claims. The receiver keeps one fixed consume endpoint; missing routes are deterministic configuration errors, 2xx confirms delivery, and non-2xx/connection failure/timeout remains retryable. Multiple receivers require a broker transport.
- Derive every inbound broker subscription from an actual Integration Event listener and identify it by `applicationName + eventName`. Remove `IntegrationEvent.subscriber` and `NONE_SUBSCRIBER`; one event type owns one RabbitMQ queue or RocketMQ consumer group per application identity, while application replicas share that same subscription identity. Duplicate resolved event names mapped to different payload classes fail startup.
- Keep `IntegrationEvent.value` as the stable semantic `eventName` only. HTTP, RabbitMQ, and RocketMQ each use one explicit transport `routes[eventName]` map for deployment topology; RabbitMQ routes provide exchange/routing key, RocketMQ routes provide topic/tag, and HTTP routes provide base URL. Missing, duplicate, or invalid effective routes are deterministic configuration failures. Do not infer destinations from event names, preserve `exchange:routingKey`/`topic:tag` annotation syntax, or add fallback routing conventions.
- Manual retry/redrive accepts only `EXCEPTION` or `EXHAUSTED` reliable Command/Event records, preserves the original logical record ID, and enters the same atomic claim state machine. It rejects `INIT`, active `EXECUTING`/`DELIVERING`, successful `EXECUTED`/`DELIVERED`, `CANCEL`, and `EXPIRED` records. Intentional re-execution or redelivery of completed or expired work uses the ordinary new `send`/`enqueue` registration path to create a new record and ID.
- Remove the write-only `__archived_command` and `__archived_event` tables, archived JPA entities/repositories, and active-to-archive migration. Keep only `__command` and `__event`; provider-owned cleanup hard-deletes terminal records in batches after a configurable retention window. Cap4k does not provide a permanent execution-history warehouse. Logs, metrics, tracing, or project-owned audit storage carry long-term evidence, and an `EXHAUSTED` record remains manually recoverable only while it is retained.
- Measure reliable Command/Event retention from the latest transition into a terminal state using an explicit `terminalAt`. Command and Event retention are separately configurable and both default to seven days. Manual recovery clears the old terminal marker while the record is actively reclaimed; if it reaches a terminal state again, the new transition resets the retention clock. Never derive retention from the work item's execution `expireAt`.
- Saga is retired from the active Runtime and shall not be restored by this audit. Historical Saga specs/plans remain design history only; the active repository has no Saga module or source capability, and the JPA starter boundary test explicitly requires the old Saga repository to be absent from the classpath.
- Retire `cap4k-ddd-console` completely, including its module, auto-configuration, direct SQL services, unauthenticated HTTP search/retry/unlock handlers, tests, and current documentation. Keep only the state-machine-validated programmatic Command/Event manual-recovery API; a project that needs an operations UI or endpoint owns its authentication, authorization, redaction, and audit boundary.
- Retire Snowflake as a built-in application-side identifier strategy. Remove the self-written algorithm, database Worker-ID dispatcher, `__worker_id` schema, heartbeat/lifecycle, Hibernate bridge, starter, configuration, Generator/catalog options, Agent API claims, tests, and public documentation. UUID7 is the only built-in application-side Strong ID allocation strategy; database-assigned identity remains a persistence policy rather than an application-side generator. A future Snowflake capability requires a separate confirmed design based on a maintained open-source implementation and must not restore the retired custom subsystem.
- Preserve the accepted external-I/O-safe Agent API boundary. `runtime.json` reports resolved Runtime artifacts/providers, static configuration evidence, exclusivity/prerequisite diagnostics, and explicit `operationalProbe: NOT_PERFORMED` / `operationalState: UNKNOWN`; it never starts Spring or probes a database/broker. Runtime startup owns deterministic provider/config validation. A provider-state registry owns actual `STARTING`/`UP`/`DEGRADED`/`RECOVERING`/`OUT_OF_SERVICE` state, and an optional Actuator adapter exposes truthful health/readiness.

# Open questions

- Author reliable Command, persisted Domain Event, and Integration Event automatic retry policy in deployment/runtime configuration. Remove `@Retry` from message payload types and keep retry policy out of Design JSON, generated skeletons, Analyzer recovery, and Drawing Board semantics. Configuration may provide common defaults plus capability/message-identity overrides; when a reliable record is created, resolve and persist its effective attempt budget, backoff policy, and execution expiry so later configuration changes do not rewrite already accepted work.

- Use one framework fallback retry policy for reliable Command, persisted Domain Event, and Integration Event. Capability-level and message-identity overrides remain available through Runtime configuration, but the framework does not embed three divergent historical fallback schedules.

- Use the balanced shared fallback for newly created reliable records: the first attempt is immediately due at `firstAvailableAt`; allow 50 total attempts including the first; retry after 1, 2, 4, 8, and 16 minutes, then capped 30-minute delays with deterministic record-ID-derived ±10% jitter; expire 24 hours after `firstAvailableAt`. Attempt-budget exhaustion enters `EXHAUSTED`, while reaching the execution deadline first enters `EXPIRED`.

- Keep inbound Integration Event receivers stateless. RabbitMQ/RocketMQ acknowledge only after all local handlers succeed and otherwise delegate redelivery, retry limits, and dead-letter handling to the selected broker/container; HTTP returns non-2xx so the sender's reliable record retries. Cap4k does not add an inbox table, consumer-side durable scheduler, delivery-progress state, or framework DLQ. Stable event IDs cross the boundary and consuming projects own business idempotency.

- Keep public cap4k `@EventListener` methods payload-only and expose transport-neutral reliable-delivery metadata through a read-only scoped `ReliableEventDeliveryContext` shared by persisted/deferred Domain Event and inbound Integration Event dispatch. It exposes stable `eventId`, `eventName`, `publishedAt`, an exact attempt only when available, and a non-authoritative redelivery hint without broker/HTTP topology or an absolute duplicate claim. Ordinary synchronous Domain Events have no such context; strict and nullable accessors distinguish active reliable delivery from absence.

- Treat persisted/deferred Domain Event delivery and inbound Integration Event delivery as the same reliable scheduled-delivery entry for Handler transaction and Unit-of-Work semantics. They differ only in the upstream confirmation boundary: a persisted Domain Event conditionally completes its local Event record, while an inbound Integration Event acknowledges the broker message or returns HTTP 2xx. Ordinary non-persistent Domain Events remain synchronous inside the originating Command transaction.

- Treat handlers invoked by persisted/deferred Domain Event delivery and inbound Integration Event delivery as synchronous controller-like adapters, not transaction roots. Runtime establishes no ambient transaction or Unit of Work around delivery. Direct Repository access remains rejected outside Command/Query invocation scopes; a handler that changes local state sends a local Command, and each outer Command owns its own transaction and Unit of Work. Completion/acknowledgement occurs only after every applicable synchronous Handler method and its Mediator-managed parallel Query/Capability tasks converge, but already committed Commands are not rolled back if a later handler fails; redelivery may re-run them, so handlers and Commands must be idempotent under the declared at-least-once contract.

- Continue to allow multiple local handlers for one reliable scheduled event delivery. Dispatch is a synchronous in-memory call chain rather than per-handler durable workflow: evaluate `condition`, invoke applicable Handlers by Spring `@Order` priority with equal values unordered, and complete the persisted Event record or acknowledge/return 2xx only after the dispatcher returns. On the first thrown failure, stop and leave the whole delivery retryable; every redelivery restarts from the first applicable Handler. Do not persist per-handler progress. Previously committed Commands may run again on redelivery and therefore remain idempotent.

- Preserve the real-project authoring requirement that one Spring bean may declare several independent method-level reactions to the same event, as demonstrated by `CustomerCoinGivenDomainEventSubscriber.on1/on2`. A single-entry `EventSubscriber<T>` contract can only represent that shape by manual fan-out or additional classes and therefore is not automatically the simpler public authoring model.

- Make method-level Spring `@EventListener` the sole public cap4k Domain/Integration Event handler contract. Preserve multiple independent listener methods in one bean. Retire `EventSubscriber<T>`, `AbstractEventSubscriber<T>`, public dynamic subscribe/unsubscribe, and the duplicate custom subscriber registry without deprecation or compatibility bridges. Cap4k listener discovery/validation applies only to methods whose payload is a cap4k Domain/Integration Event; general Spring events remain untouched. Cap4k handlers are synchronous, payload-only, `Unit`/`void` methods; class/method `@Async`, `@TransactionalEventListener`, returned-event publication, and other detached completion models are unsupported.

- Define every cap4k Handler invocation as synchronous: `@EventListener`, `CommandHandler`, Query Handler, and Capability Handler complete when their method returns and do not use `@Async`, `suspend`, Future/Reactive completion, or manual fire-and-forget as framework-managed work. Reserve “asynchronous” exclusively for Mediator scheduling/durable handoff. `Mediator.commands.send` synchronously invokes a Command Handler now; `enqueue/schedule/delay` synchronously registers a reliable Command record, and the scheduler later invokes that same ordinary synchronous Command Handler.

- Allow a synchronous cap4k `@EventListener` to call `Mediator.commands.enqueue/schedule/delay` directly. If a cap4k Command Unit of Work is active, reliable Command registration joins its transaction and becomes visible only with the originating state change. Otherwise an Event Handler registration runs in a provider-owned short transaction that persists the reliable Command record and commits before returning. Persistence failure throws through the synchronous Event Handler; later scheduled execution invokes an ordinary synchronous Command Handler in its own transaction.

- Do not add producer-side Reliable Command deduplication, an explicit `deduplicationKey`, or automatic keys derived from source event/listener/command identity. Every successful `enqueue/schedule/delay` is a new reliable registration; event redelivery may register another record. Stable source event IDs remain available through delivery context so projects can carry them into Commands and implement business idempotency. This intentionally preserves at-least-once semantics and avoids a partial deduplication layer that still cannot prevent ambiguous command re-execution.

- Replace public outbound Integration Event `Mediator.events.attach/detach` with `enqueue/schedule/delay`. Registration is synchronous and network publication remains scheduled: when a Command Unit of Work is active, the outbox record joins that transaction; otherwise a synchronous Event Handler uses a provider-owned short outbox transaction that commits before returning the event ID. Persistence failure propagates through the Handler. Every committed registration is a new event record, so source redelivery may register another and downstream idempotency remains required.

- Give each manual redrive of an `EXHAUSTED` reliable Command/Event exactly one additional claim opportunity. Preserve the original logical ID and attempt history, do not restart the 50-attempt/24-hour automatic policy, and let this explicit operator authorization bypass the exhausted automatic deadline for that one claim. Success completes the record; failure returns it to `EXHAUSTED`, resets `terminalAt`, and requires another explicit redrive for another attempt.

- Treat synchronous cap4k Event Handlers like controllers for local Mediator access. They may call synchronous `commands.send`, `queries.ask`, and `capabilities.call`, and may use `queries.askAsync` / `capabilities.callAsync` for structured parallel fan-out inside the same Handler invocation. The Handler awaits the required futures, combines their results, and only then invokes the dependent `commands.send` or registers it through `commands.enqueue/schedule/delay`; every local task must converge before the Handler is complete. This is parallel execution within a synchronous Handler, not detached fire-and-forget or reliable scheduling.

- Retire reliable Command `Mediator.commands.result(id)` and remove persisted result payload/type fields. Synchronous `commands.send` continues to return its Handler result, while `enqueue/schedule/delay` returns only the reliable registration ID. A reliable Command is fire-and-forget at the Runtime task boundary; business completion is observed through domain state, Query, Domain Event, or Integration Event rather than a temporary Runtime result warehouse.

- Track every `queries.askAsync` / `capabilities.callAsync` task started through Mediator in the current Event Handler scope. After the method body returns, Runtime automatically waits for all scoped tasks before declaring the Handler complete; any task failure fails the Handler and propagates to the surrounding transaction or reliable delivery/ack boundary. Business code still explicitly awaits results before using them to construct and `send` or reliably register a dependent Command. Manually spawned threads, coroutines, executors, or reactive subscriptions remain outside this managed scope.

- Do not add retryable/non-retryable exception classification for accepted reliable Command/Event execution. Every execution exception follows the effective retry policy snapshotted into the record. Deterministic configuration, type, route, codec, and payload defects fail at startup or registration instead; an expected business refusal is expressed as a normal business result/no-op/event rather than an execution exception. Runtime exposes neither `NonRetryableExecutionException` nor a project `FailureClassifier`.

- Renew an active reliable Command/Event claim lease while its synchronous Handler is executing. Only the current claim token may renew or write the terminal result. Process death stops renewal, and another instance may atomically reclaim after lease expiry. Renewal failure or lease loss keeps provider health truthful and rejects stale completion; already-produced side effects remain an at-least-once ambiguity rather than being presented as rolled back.

- Persist only bounded safe failure facts in reliable Command/Event records: `failureId`, exception type, failure time, attempt, and status. Do not persist exception messages, stack traces, or a duplicate payload as failure detail. Emit full diagnostic detail only to correlated structured logs/traces, never expose raw payloads through transport failure logging, and let programmatic recovery surfaces return only the safe record facts.

- Support a strict cap4k subset of method-level Spring `@EventListener`: exactly one concrete cap4k Domain/Integration Event parameter and `Unit/void` return; reject `classes` multi-event declarations and supertype/polymorphic subscriptions. Permit non-blank Spring `condition` SpEL as handwritten Runtime filtering policy, but do not project or round-trip it through Design JSON, generated skeleton semantics, Analyzer, or Drawing Board. One bean may still declare multiple independent listener methods for the same concrete event.

- Use one transport-neutral scoped `ReliableEventDeliveryContext` for persisted/deferred Domain Event and inbound Integration Event delivery. It exposes stable `eventId`, `eventName`, `publishedAt`, an exact delivery attempt only when available, and a non-authoritative `UNKNOWN/FIRST/REDELIVERED` hint. Ordinary synchronous Domain Events have no reliable delivery context. The context never exposes broker/HTTP topology or claims authoritative duplicate detection; strict and nullable accessors distinguish active reliable delivery from absence.

- Honor Spring `@Order` as handwritten Runtime policy for matching local cap4k Handler methods within one application and one delivery attempt. Lower values run first; equal values have no guaranteed order, and every redelivery starts again from the first applicable Handler. This creates no cross-message, cross-instance, cross-service, or transactional ordering guarantee. Like `condition`, `@Order` is not Design JSON, generated-skeleton semantics, Analyzer recovery, or Drawing Board content.

- The user confirmed the complete Runtime target contract on 2026-08-03 as the shared understanding for closing the Runtime audit slice and preparing independent implementation/fix branches. This confirmation does not authorize production-code changes on the audit branch, advance the overall Comet change out of Shape, start Analyzer audit before merged Runtime fixes are refreshed and reverified, or begin downstream real-project validation.
