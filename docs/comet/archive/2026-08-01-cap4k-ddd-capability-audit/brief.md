# Outcome

形成一份可复核的 cap4k DDD 能力审计，回答：cap4k 是否足以作为从问题空间战略设计到解决方案空间战术设计、实现与验证的承载框架；哪些能力由 cap4k 一等支持，哪些只由 skill/方法支持，哪些需要手写约定或外部提供者，哪些仍是明确缺口。

审计还必须回答战略设计向战术设计翻译时的实际摩擦：战略产物能否被 skill 低成本、可追踪地投影为 cap4k 战术载体、生成器输入、手写逻辑位置和验证证据。

# Scope

- 审计当前 `origin/master` 上的 cap4k 源码、生成器契约、运行时边界、仓库内 authoring skills、公开 backlog 与最新相关规格。
- 以《实现领域驱动设计》的完整核心体系为审计基准：领域/子域、限界上下文、上下文映射、架构，以及实体、值对象、领域服务、领域事件、模块、聚合、工厂、仓储、限界上下文集成和应用层。
- Event Sourcing、独立 CQRS 读模型、Process Manager/Saga、模块运行时等现代扩展作为附录评估，不作为本轮“够用”的硬门槛。
- 将 DDD 概念按战略设计、战术建模、应用编排、限界上下文集成与验证落地分类。
- 对每个概念分别判断 cap4k 四块能力：skill、生成器、运行时、分析器，以及它们之间的交接和真实项目证据。
- 产出“可以直接优化 skill / 需先补 cap4k / 可通过外部能力承载”的分流结论。

# Non-goals

- 本 change 不直接修改现有 cap4k authoring skills。
- 本 change 不实现新的框架、生成器、运行时或示例项目能力。
- 不把战略设计判断错误地归责为框架代码缺陷，也不要求每个 DDD 概念都有注解、生成器或运行时类型。
- 不用历史规格替代当前源码和当前 backlog 事实。

# Acceptance examples

- 给出“限界上下文”时，报告必须区分：cap4k 能否在一个上下文内实现模型、能否表达跨上下文契约、是否能生成或验证上下文地图，而不是只给一个总的支持/不支持。
- 给出“聚合、实体、值对象、领域服务、领域事件、工厂、仓储”时，报告必须逐项标注生成器、运行时和手写业务逻辑边界。
- 给出“Shared Kernel、Customer/Supplier、Conformist、ACL、OHS、Published Language”等上下文映射模式时，报告必须说明哪些是组织/设计决策、哪些有 cap4k 技术载体。
- 最终结论必须明确回答“现在是否足以开始优化完整 DDD skill”，并列出开始前必须接受或补齐的前置条件。
- 对一个已确认的限界上下文，skill 必须能够将聚合、用例、领域事实、外部关系和上下文集成决策映射到 cap4k carrier/input/skeleton/evidence；报告必须指出重复录入、人工转换或信息损失发生在哪里。
- 对一个已经实现的业务流程，分析器必须被单独审计：它能否观察结构、调用或因果链，能否帮助 skill 发现战略/战术/实现漂移，以及它不能证明哪些业务语义。

# Constraints and invariants

- 结论以当前 `origin/master`、当前 GitHub issue 状态和当前仓库契约为准。
- cap4k 的稳定定位是 DDD 战术框架加生成器支持的 authoring system；生成器不能替代人的领域判断。
- 战略设计产物与战术代码载体必须分层审计，不能用“能手写”冒充“一等支持”。
- 当前明确边界保持不变：无内建 Saga；持久化长流程需外部 provider；Sibling design-entry 类型引用仍不支持；短名解析保持保守；分析输出是证据而非业务输入真相。
- 审计结论必须披露未运行的验证，不得把静态审查表述为完整运行验证。
- 战略设计由 skill 与人协作完成；战术设计由 cap4k 运行时和生成器协作落地；从战略到战术的翻译仍由 skill 协作，但 cap4k 应通过清晰且足够完整的战术载体降低翻译成本。
- cap4k 能力审计以四块协作为整体：skill 负责协作与翻译，生成器负责结构投影，运行时负责执行语义，分析器负责实现后的观察、验证与反馈。

# Decisions

- 使用四层能力视角：方法/skill、模型/源码表达、运行时、生成器与证据。
- 使用 `strong`、`partial`、`external/provider`、`missing/not-first-class` 四类状态，避免笼统的“支持”。
- 本轮只做能力审计与后续 skill 优化门槛定义，不进入现有 skill 实施。
- 用户确认选择 A：审计以《实现领域驱动设计》的完整核心体系为强制基准；现代 DDD 扩展进入附录，不决定核心“够用”结论。
- “够用”采用职责分层标准：战略设计不要求 cap4k 建立一等运行时类型，由 skill 保存并协作；cap4k 必须足以承接战术设计；skill 负责战略到战术的翻译。
- 运行时框架质量的一项核心评价是翻译成本：cap4k 战术载体越完整、边界越清晰，skill 从战略产物投影到代码和生成器输入的成本应越低。
- 用户确认选择 A：低翻译成本以结构化、可追踪的半自动投影为标准；领域判断保留人工确认，确认后的生成器输入可以由 skill 投影。
- 审计必须覆盖 cap4k 四层能力：skill、生成器、运行时、分析器；不能把分析器折叠到普通验证证据中。
- 用户确认选择 A：分析器是观察、验证和漂移反馈能力；分析产物返回 skill 供人判断和回滚，但不直接成为生成器的权威业务输入。
- 四块闭环采用 `skill 决策与翻译 -> generator 结构投影 -> runtime 战术执行 -> analyzer 观察反馈 -> skill 判断与回滚`。
- 用户已确认当前 Outcome、Scope、决策、验收示例、约束和非目标构成完整 shared understanding，可以据此进入能力审计。

# Verification expectations

- 静态核对 repo-local skill 路由与所有相关 focused skill 契约。
- 静态核对运行时/生成器源码中的一等接口、模型、注解、planner 与模板证据。
- 核对当前 GitHub backlog 中未完成的能力和验证债务。
- 以概念矩阵、证据引用、残余风险和明确门槛给出结论；未运行编译/测试时明确标记为静态审计。
