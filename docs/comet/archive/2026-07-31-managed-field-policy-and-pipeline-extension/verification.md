# Spec consistency

The implementation matches the confirmed Comet contract and complete implementation scope. It retains the fixed pipeline, provides one root Pipeline Extension SPI with declarative contributions, resolves exact managed-field policy keys into the canonical model, generates runtime catalog metadata, assigns application IDs no later than aggregate admission, and stabilizes JPA changes as candidate detection, enrichment, final dirty detection, then flush.

The final design spec records the two review corrections: creation input is legal only when INSERT authority is caller, framework, or managed-handler owned; and each enricher is guarded against mutations to every managed persistence-context entity, including collection changes on entities loaded during enrichment.

No public multi-persistence-provider SPI, read-model contract, or tenant-wide query-isolation promise was introduced. Checked-in Factory and Behavior generation continues to use authoritative `SKIP` behavior.

# Known limitations and risks

- The supported persistence implementation remains JPA/Hibernate. Pipeline Extension is available now, while a public multi-provider persistence SPI remains deferred until a second provider creates concrete requirements.
- Database-generated policies are covered by planning, rendering, compilation, and provider-oriented lifecycle tests, but not yet by one real database insert/update readback test.
- Semantic time adapters are covered in resolver and registry layers. There is no single end-to-end `Instant` to `LocalDateTime` catalog-to-Spring-to-UoW-to-flush test yet.
- There is no dedicated Spring startup test for every invalid admission-only custom-accessor footprint; resolver and registry validation cover the underlying constraints.
